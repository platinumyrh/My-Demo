# 第 4 章 经济可行性分析

本章方法论先行说明。本项目为课程设计，无资金投入与商业收入，故不采用货币度量，统一以投入工时（人时）作为成本单位，以可复用资产节省的后续工时与能力收益作为效益单位。全章不出现金额，非人力投入只描述可获得性，不做折算。

## 4.1 支出（投入）

投入以人力工时为主体。工作量基准按 5 人、16 周、每人每周 10 小时拟定，合计 800 人时；若每周投入工时调整，各阶段人时按同比例折算，阶段间相对比例不变。各阶段分配见表 4-1。

| 阶段 | 内容 | 工期 | 人时 |
|---|---|---|---|
| M0 | 需求分析与技术选型 | 第 1 周 | 40 |
| M1 | 联机骨架（UDP + Protobuf + 心跳 + 登录） | 第 2 周 | 60 |
| M2 | 确定性基础库（定点数 / 环绕角 / 查表三角 / 确定性随机） | 第 3 周 | 60 |
| M3 | 逻辑世界（移动 / 转向 / 跳跃 / 碰撞 / 边界） | 第 4–5 周 | 100 |
| M4 | 战斗结算（命中 / 伤害 / 弹药 / 换弹 / 死亡） | 第 6 周 | 60 |
| M5 | 协议编解码（指令批量打包与还原） | 第 7 周 | 40 |
| M6 | 服务端中继（座位分配 / 封帧泵 / 超时补空） | 第 8 周 | 80 |
| M7 | 客户端预测与回滚（输入延迟 / 预测 / 快照回滚重演） | 第 9–10 周 | 100 |
| M8 | 表现层与动画（插值渲染 / 动画 / 特效 / UI） | 第 11–12 周 | 100 |

| M10 | 资源热更新与编辑器工具 | 第 14 周 | 60 |
| M11 | 集成测试、文档与交付 | 第 15–16 周 | 40 |
| **合计** | | **16 周** | **800** |

[[FIG:fig_workload|图 5 各阶段工作量分布图]]

分配结构有三点需说明。其一，核心难点为 M2 确定性基础库、M3 逻辑世界、M6 服务端中继与 M7 预测回滚，四阶段合计 340 人时，约占整体四成。其二，M3 与 M7 各 100 人时且跨两周，不宜压成单周冲刺。其三，M8 表现层与动画同为 100 人时，可裁剪性最强，是敏感性分析的首要对象。

非人力投入只描述可获得性。Unity 2022.3 LTS 个人版、.NET 8、protoc 与 Git 均可免费获得；硬件使用成员自有开发机与实验室机器；素材采用标注可免费商用的开放授权资源；服务器与网络使用校内实验室局域网，不租用公网资源。因此支出即 800 人时。

## 4.2 收益（效益）

本项目的直接经济收益为 0：课设成果不投入商业运营，不产生销售收入，效益评估须转向时间、能力与成果三类。

1. **时间收益（可复用资产）**：项目将沉淀确定性帧同步框架、联机骨架、资源热更新与自测工具链，其中帧同步框架含定点数库、确定性随机数、固定结算顺序与状态哈希校验，可复用于后续同类开发，预计节省重复投入约 200 人时以上。
2. **学习成本回收**：网络编程与确定性模拟是团队现有缺口，前期学习工时已并入 M0 至 M7，不额外单列；随框架成型，后期开发效率将显著提升，表现为表现层、房间闭环与工具链阶段单位功能耗时下降。
3. **能力收益**：团队将在网络同步、确定性模拟、工具链建设与工程规范四方面形成可迁移能力，涵盖封帧、输入延迟、回滚重演、快照还原与资源增量更新等问题。
4. **成果收益**：可预期成果包括课程设计成绩与学分、作品集素材，以及潜在的学科竞赛与展示机会；该部分无法用工时量化，但属效益的重要组成。

## 4.3 支出收益分析

时间口径下，总投入 800 人时，可量化时间收益 200 人时以上，另有能力与成果收益为定性收益。仅看可量化部分，投入约为收益的四倍；但 800 人时中的大部分转化为能力沉淀与课程学分，200 人时以上是额外形成的复用价值，二者合并看投入产出关系成立。

实现路径上存在自研与采购两条路线，时间维度对比见表 4-2。

| 方案 | 开发人时 | 学习成本 | 自主可控 | 说明 |
|---|---|---|---|---|
| 采购商业同步方案 | 较低 | 中（需熟悉其 API 与配额限制） | 低 | 依赖第三方授权与计费规则 |
| 自研确定性帧同步（选定） | 高（约 800 人时） | 高（需攻克确定性） | 高 | 知识点完整、可复用、无授权约束 |

本项目拟选定自研确定性帧同步方案。其投入人时虽最多，但知识点覆盖最完整，涵盖传输层、协议编解码、确定性模拟到预测回滚的全部环节，契合课设对知识综合运用的要求；成果以源码沉淀可复用，且无授权约束。采购方案开发人时较低，但自主可控性低，学习内容被封装在接口之后。

课设执行中人力与周期存在波动，敏感性分析见表 4-3。

| 情形 | 投入规模变化 | 削减方案 | 结论 |
|---|---|---|---|
| 每周工时 10 h 降至 8 h | 总工时降至 640 | 削减资源热更与表现层内容 | 核心联机闭环仍可交付 |
| 周期压缩至 12 周 | 周期缩短 4 周 | 房间人数降为 2 人、关闭资源热更 | 保留确定性帧同步与预测回滚 |
| 人力减至 3 人 | 人数减少 2 人 | 5 套自测套件缩减为 3 套（基础库、逻辑世界、协议） | 关键自测闸门仍保留 |

三种情形思路一致：优先保留确定性帧同步与预测回滚这条技术内核，优先削减表现层与资源热更新，并在人力紧张时按基础库、逻辑世界、协议的优先级裁剪自测套件而非取消自测，自测套件即进度闸门。无论何种情形，核心联机闭环均可交付，结论不反转。

# 第 5 章 技术可行性分析

## 5.1 主要技术路线

本项目拟采用"Unity 客户端 + 自研 C# 服务端 + 编辑器工具链"的三段式架构，定位为俯视角、单房 4 人、15Hz 逻辑帧的确定性帧同步多人在线 FPS 对战系统，并明确不做公网运营与商业化、不做匹配排位与社交、不做大规模并发。技术栈见表 5-1。

| 项 | 拟定选定方案 |
|---|---|
| 客户端引擎 | Unity 2022.3 LTS（个人版，无授权费用） |
| 客户端语言 | C# |
| 服务端 | .NET 8 控制台程序（C#，跨平台） |
| 输入 | Unity Input System |
| 相机 | Cinemachine |
| UI 文本 | TextMeshPro + UGUI |
| 序列化 | Google.Protobuf（Protocol Buffers 3） |
| 协议代码生成 | protoc |
| 版本管理 | Git |

**网络层方案。** 传输层拟采用 UDP 而非 TCP，并自研轻量可靠性策略。默认端口拟为 7777；包格式统一为 MsgID(4 字节) + Length(4 字节) + Protobuf 载荷。容量目标拟定为单服 20 在线、100 房间、每房 4 人，客户端拟每 2 秒发送一次心跳。协议编号拟分区段规划：心跳 1–2、房间管理 10–20、第一代帧同步 30–31、游戏控制 50–51、登录 70–71、战斗事件 80–83、第二代帧同步主方案 90–91。

**同步方案选型论证。** 第一代拟采用状态同步：客户端上报位置，服务端汇总后广播状态快照，远端插值校正。问题有三：位置由客户端上报，不具权威性，存在作弊空间；各端状态由插值而来，可能出现不一致；状态快照需携带全部玩家状态，带宽随玩家数线性增长。现比较三个候选方案，见表 5-2。

| 方案 | 确定性 | 带宽 | 防作弊 | 学习成本 | 开发人时 |
|---|---|---|---|---|---|
| 状态同步 | 弱（依赖插值校正，难以逐帧一致） | 高（状态快照随玩家数线性增长） | 弱（位置由客户端上报） | 中 | 中 |
| 确定性帧同步（选定） | 强（同种子、同指令、同结果） | 低（仅上行量化输入指令，单条约十余字节） | 较强（客户端只上报输入，不掌握权威状态） | 高 | 高（约 800 人时） |
| 采购商业同步方案 | 由产品内部实现决定，外部不可控 | 由产品策略决定 | 较强（一般为服务端权威） | 中（需熟悉其 API 与配额限制） | 较低 |

对比后选定第二代确定性帧同步方案：客户端只上报量化输入指令，服务端不持有游戏状态、只做封帧与广播，各客户端用同一份确定性逻辑与同一批指令独立演算，得到完全一致的结果，既消除作弊与不一致空间，也把上行带宽压到指令量级。

**确定性设计。** 确定性是选定方案能否成立的前提，拟从七方面保证。

1. 定点数运算：拟自定义 Q16.16 定点数类型并重载四则运算，1 单位对应 1 米、精度约 1/65536 米，规避跨平台浮点差异。
2. 角度量化：角度拟用 uint16 环绕角表示，0–65535 映射 0–360°；三角函数用预计算查表。
3. 确定性随机数：拟自定义随机数发生器，同一种子必产生同一序列。
4. 固定遍历顺序：玩家按 ID 升序遍历，碰撞配对按 ID 升序生成，命中判定在距离相同时取 ID 较小者。
5. 逻辑帧内固定结算顺序，顺序即协议、不可随意调整：按 ID 升序逐个移动积分（缺指令按空指令处理，不卡帧），随后战斗结算（冷却、换弹、开火、命中、伤害、死亡），再执行两轮圆形碰撞互推，最后做边界钳制。
6. 状态哈希：对帧号、玩家 ID、坐标、朝向、血量、弹药、生死做混合哈希，用于跨端漂移比对。
7. 逻辑层与服务端拟共用同一份不含 UnityEngine 依赖的纯 C# 源码，保证两端逐位一致。

**客户端预测与回滚机制。** 帧同步需等待其他玩家指令，故拟采用输入延迟加本地预测。输入延迟拟为 2 帧，即本地第 N 帧指令在第 N+2 帧生效，约 133 毫秒；客户端先行预测并保存该帧快照，权威指令到达后若与预测不符，则回滚到分歧帧前一快照并重演。预测超前上限拟为 8 帧，防断流空转。

**服务端无状态中继。** 服务端拟为无状态中继，不持有游戏状态，只负责指令收集与封帧广播：某帧全员指令到齐即封帧下发，200 毫秒到期仍缺则补空指令封帧推进，不因单个玩家卡住全场。座位拟按加入顺序分配，各端据此取确定性出生点；玩家掉线后其座位由空指令补位。服务端拟为跨平台控制台程序。

**资源与热更新方案。** 资源拟用 AssetBundle 按目录打包，增量更新采用资源对比文件：打包时逐包记录包名、字节数与 MD5，运行时下载远端对比文件比对，MD5 不同才下载，服务端已移除的包在本地删除。加载路径优先级拟为持久化目录（热更结果）优先、StreamingAssets（随包首版）兜底；资源访问统一走资源加载门面，含引用计数与依赖管理。脚本热更拟预留 Lua 能力并集成绑定库与多平台原生库，本期只做集成不做业务接入。

**关键参数。** 拟定核心参数见表 5-3。

| 参数 | 取值 | 说明 |
|---|---|---|

## 5.2 技术可行性分析

1. **技术成熟度**：所选技术均为成熟且资料完备的既有技术：Unity、C#、.NET、Protocol Buffers 与 Git 均有官方文档与社区资料；确定性帧同步是业界成熟方案，在即时战略与 MOBA 类游戏中广泛采用，有公开文献与实现可参考。因此不存在"无人做过"的技术环节，风险主要来自实现细节的严谨程度。
2. **团队能力与学习曲线**：小组已具备 C# 与 Unity 开发经验及基础游戏逻辑能力，待补齐 UDP 网络编程、确定性模拟与定点数运算、多线程服务端三项。对策是把学习拆分到各里程碑并以自动化自测作为验收闸门：M2 以基础库、M3 与 M4 以逻辑世界与战斗、M5 以协议、M7 以预测自测为闸门，全绿方可进入下一阶段。
3. **性能可行性**：4 人规模下移动积分、命中判定与碰撞互推均为 O(N²) 且 N=4，计算量极小，15 Hz 下 CPU 占用可忽略。带宽估算上，单条压缩后的输入指令约十余字节，4 人 × 15 帧/秒，单客户端上行量级为每秒数百字节到 1 KB 以内，下行含多帧合包为每秒数 KB 量级，远低于局域网承载能力。渲染方面，逻辑帧与渲染帧拟解耦，渲染帧在相邻逻辑帧状态间插值显示，帧率不受 15 Hz 制约。上述均为估算，实现阶段复核。
4. **测试可行性**：拟建立 5 套分层自测套件，编辑器菜单一键运行，约 50 条断言，覆盖确定性基础库、逻辑世界（双世界 300 帧逐帧状态哈希一致、位移定量、碰撞互推对称、边界钳制）、客户端预测（预测落空触发回滚且校正后终态与参照一致、乱序与重复投递、快照保真）、战斗逻辑（开火节流、命中与落点、最近目标优先、击杀判定、死者不挡弹）与协议转换（单条与批量往返、全链路回环）。判据拟以状态哈希逐帧比对为核心；另拟安排 4 人同房人工联机测试，验证手感、同步表现与异常恢复。
5. **依赖与许可可获得性**：Google.Protobuf 采用 BSD 系许可证，Lua 绑定库采用 MIT 许可证，均可在课设中免费使用并保留版权声明；Unity 个人版在课设与学习用途下无授权障碍；.NET 8、protoc 与 Git 均可免费获得。美术与音频素材拟只采用标注可免费商用的开放授权素材并登记来源与许可证。
6. **技术风险与对策**：主要技术风险及拟采取的对策见表 5-4。

| 风险 | 影响 | 对策 |
|---|---|---|
| 跨平台浮点差异导致不同步 | 严重（表现撕裂、判定不一致） | 全逻辑层使用定点数 + 查表三角函数 + 确定性随机；禁用逻辑层浮点 |
| UDP 丢包与乱序 | 中（指令延迟或缺失） | 权威帧缓冲支持乱序与重复；超时补空指令；客户端预测遮盖延迟 |
| 客户端预测落空 | 低（画面轻微回跳） | 快照回滚重演，回滚后终态与权威一致；限制预测超前上限 8 帧 |
| 团队缺乏网络与确定性经验 | 高（进度风险） | 分阶段学习 + 每阶段自测闸门 + 里程碑评审 |
| 美术素材不足 | 中（观感受限） | 采用开放授权素材，优先保证功能完整 |
| 无公网服务器 | 中（演示受限） | 以内网/回环演示为主，服务端为控制台程序，局域网内任意机器可作服务端 |
| 进度延期 | 高 | 范围冻结 + 敏感性预案（削减房间人数、关闭热更、缩减自测套件） |

影响等级为严重或高的三项风险分别对应确定性、团队能力与进度，恰为技术路线的三个关键点。对策思路是把不确定性前置消化：确定性风险在 M2 阶段用定点数与查表解决，能力风险用阶段闸门化解，进度风险用范围冻结与敏感性预案兜底，因此本项目技术可行。
