### 3.5 确定性设计（报告的技术亮点，务必写清）
1. **定点数运算**：自定义 Q16.16 定点数类型，重载四则运算，彻底规避不同平台/CPU 的浮点差异。
2. **角度量化**：角度用 uint16 环绕表示，三角函数采用**预计算查表**，不使用运行时浮点三角函数。
3. **确定性随机数**：自定义确定性随机数发生器，同种子必产生同序列。
4. **固定遍历顺序**：逻辑世界中玩家按 ID 升序排列与遍历；碰撞配对环境按 ID 升序；命中判定同距离时取 ID 较小者（确定性平手规则）。
5. **逻辑帧内固定结算顺序**（顺序即协议，不可随意调整）：
   ① 按 ID 升序逐个移动积分（缺指令按空指令处理，不卡帧）
   → ② 战斗结算（冷却/换弹/开火/命中/伤害/死亡，基于移动后位置）
   → ③ 圆形碰撞互推（执行两轮，缓解多人堆叠残留）
   → ④ 世界边界钳制
6. **状态哈希**：对帧号、玩家 ID、坐标、朝向、血量、弹药、生死做纯整数混合哈希，用于跨端漂移比对。
7. **逻辑层与服务端共用同一份纯 C# 源码**（不含 UnityEngine 依赖），保证两端模拟逐位一致。

### 3.6 两代同步方案的取舍（第 5 章选型论证的核心材料）
- **第一代（状态同步）**：客户端上报位置，服务端广播状态快照，远端插值校正。
  问题：位置由客户端上报不具权威性，存在作弊与不一致空间；带宽随玩家数线性增长。
- **第二代（确定性帧同步，主方案）**：
  - 客户端只上报**输入指令**（量化后的移动轴、瞄准角、按钮位）
  - 服务端**不持有游戏状态**，只做"封帧 + 广播"：某帧全员指令到齐就立即封帧，到期（200 ms）仍缺则补空指令封帧
  - 各客户端用同一份确定性逻辑与同一批指令独立演算出完全一致的结果
  - 客户端做**本地预测**消除输入延迟手感；权威指令到达后发现预测有误则**回滚到分歧帧前一快照并重演**
- 报告需给出**三方案对比表**：状态同步 / 确定性帧同步 / 采购商业同步方案，从确定性、带宽、防作弊、学习成本、开发人时五个维度比较，说明选第二代方案的理由。

### 3.7 资源与热更新（拟定方案）
- 资源组织：**AssetBundle** 按目录打包
- 增量更新：打包时生成**资源对比文件**（逐包记录 `包名 字节数 MD5`），运行时下载远端对比文件与本地比对，
  **MD5 不同才下载**；服务端已移除的包在本地删除
- 加载路径优先级：**持久化目录（热更结果）→ StreamingAssets（随包首版）**
- 运行时资源访问统一走一个资源加载门面（加载/异步加载/实例化/卸载 + 引用计数 + 依赖管理 + 可开关的缓存）
- 脚本热更：**预留 Lua 脚本热更能力**（集成 Lua 绑定库与多平台原生库），本期**只做集成不做业务接入**
- 编辑器侧提供三件工具：一键生成资源对比文件、把资源与对比文件发布到文件服务器、打开资源打包工具窗口

### 3.8 编辑器工具与自测（第 3 章"工具链"模块素材）
- 资源打包工具窗口、资源对比文件生成工具、资源上传工具
- 事件总线可视化检视窗口（运行时查看事件订阅关系）
- 角色/载具配置导出工具（把配置资产导出为 JSON 供服务端读取）
- **5 套确定性自测套件**（编辑器菜单一键运行，约 50 条断言）：
  1. 确定性基础库自测：定点数四则与精度、方向表全角度抽检、环绕角差、开方精度、随机数同种子同序列
  2. 逻辑世界自测：双世界 300 帧逐帧状态哈希一致、指令敏感性、走/冲刺位移定量、斜向归一化、
     转向限速不超调、碰撞互推对称且中点守恒、完全重合兜底、死亡不响应指令、边界钳制、跳跃落地不穿地
  3. 客户端预测自测：即时确认零回滚、预测命中零回滚、预测落空触发回滚且**回滚校正后终态与参照一致**、
     乱序投递、重复投递幂等、迟到指令回滚生效、发送队列一次性取走、快照还原保真
  4. 战斗逻辑自测：开火节流、直射命中与落点、反向与超射程未命中、最近目标优先、
     击杀判定、死者不挡弹（穿透）、死亡射手停火、空仓自动换弹、手动换弹、
     含战斗的随机 300 帧双世界一致、战斗敏感性
  5. 协议转换自测：单条与批量指令往返、字节级收发往返、以及**全链路回环**
     （客户端发送 → 打包上线 → 服务端顺序封帧 → 回线喂回客户端 → 断言终态与直连参照一致）

## 4. 场景与用户流程（第 3 章素材）

`登录(Login)` → `大厅(Lobby)` → `房间(Room)` → `对战(Main)`

1. **登录**：输入账号密码 → 连接服务器 → 登录校验 → 成功后进入大厅
2. **大厅**：创建房间 或 拉取房间列表并加入；列表展示房间号、房间名、房主、人数、状态
3. **房间**：展示房间信息与成员列表；房主可点击"开始游戏"；成员可离开房间
4. **对战**：服务器下发开局种子与座位表 → 各端按座位取确定性出生点 → 15Hz 逻辑帧推进 → 渲染帧插值显示

## 6. 技术可行性（第 5 章）要点

### 6.1 技术成熟度
- Unity、C#、.NET、Protocol Buffers、Git 均为成熟且资料完备的技术
- 确定性帧同步是业界成熟方案（即时战略与 MOBA 类广泛采用），有公开文献与开源实现可参考
- 无"无人做过"的技术环节，全部为可检索、可复现的已知方案

### 6.2 团队能力与学习曲线
- 已具备：C# 与 Unity 使用经验、基础游戏逻辑开发能力
- 待补齐：UDP 网络编程、确定性模拟与定点数运算、多线程服务端
- 对策：把学习拆分到各里程碑，**每个阶段以自动化自测作为验收闸门**（自测全绿才进入下一阶段），
  把能力风险切成小块，避免后期集中爆雷

### 6.3 性能可行性（给估算，注意是估算不是实测）
- 逻辑负载：4 人规模下，单逻辑帧的移动积分、命中判定与碰撞互推均为 O(N²) 且 N=4，计算量极小；
  15 Hz 即每秒 15 次，CPU 占用可忽略
- 网络带宽估算：单条压缩后的指令约十余字节，4 人 × 15 帧/秒，
  单客户端上行带宽量级为**每秒数百字节到 1 KB 以内**，下行（含多帧合包）为**每秒数 KB 量级**，
  远低于校园网与局域网承载能力
- 渲染：逻辑帧与渲染帧解耦，渲染帧在相邻两个逻辑帧状态间插值，客户端帧率不受 15 Hz 制约

### 6.4 风险与对策表（写进报告）
| 风险 | 影响 | 对策 |
|---|---|---|
| 跨平台浮点差异导致不同步 | 严重（表现撕裂、判定不一致） | 全逻辑层使用定点数 + 查表三角函数 + 确定性随机；禁用逻辑层浮点 |
| UDP 丢包与乱序 | 中（指令延迟或缺失） | 权威帧缓冲支持乱序与重复；超时补空指令；客户端预测遮盖延迟 |
| 客户端预测落空 | 低（画面轻微回跳） | 快照回滚重演，回滚后终态与权威一致；限制预测超前上限 8 帧 |
| 团队缺乏网络与确定性经验 | 高（进度风险） | 分阶段学习 + 每阶段自测闸门 + 里程碑评审 |
| 美术素材不足 | 中（观感受限） | 采用开放授权素材，优先保证功能完整 |
| 无公网服务器 | 中（演示受限） | 以内网/回环演示为主，服务端为控制台程序，局域网内任意机器可作服务端 |
| 进度延期 | 高 | 范围冻结 + 敏感性预案（削减房间人数、关闭热更、缩减自测套件） |

### 6.5 测试可行性
- 分层自测：确定性基础库 → 逻辑世界 → 战斗 → 协议 → 全链路回环，均由编辑器菜单一键运行
- 正确性判据：以**状态哈希逐帧比对**为核心判据（而非抽样）
- 人工联机测试：4 人同房实际对战，验证手感、同步表现、异常恢复

## 7. 社会可行性（第 6 章）要点

### 7.1 法律与政策
- 软件与引擎许可：Unity 个人版在课设与学习用途下无授权障碍；开源库均需核验许可证并保留声明
- 美术与音频素材：只使用明确标注可免费商用的素材来源（如 CC0），并**逐项登记来源与许可证**
- 第三方库：Protocol Buffers（BSD 系）、Lua 绑定库（MIT）等，均需在文档中列明并保留版权声明
- 内容合规：无血腥暴力渲染、无赌博与内购机制；**仅在校园内演示，不公开发行**，因此不涉及版号与运营资质
- 数据与隐私：仅使用临时测试账号，不采集任何真实个人信息；账号口令以哈希方式存储
- 学术诚信：所有引用与素材来源均登记致谢，不使用未授权的代码与资源

### 7.2 社会公共环境
- 校园网络与实验室条件足以支撑局域网多人演示
- 目标用户（同学与评审教师）对多人在线对战形式接受度高
- 同类课程设计多为单机项目，**"可联机"构成明显差异化**
- 硬件门槛低，普通笔记本电脑即可运行，便于答辩现场演示
- 可向学习社区分享技术总结（帧同步实现要点），具备正向外部性

### 7.3 操作可行性
- 使用门槛：WASD + 鼠标操作，流程为"登录 → 房间 → 开战"三步
- 部署难度：服务端为单文件控制台程序，双击即可启动；客户端无需安装数据库或中间件
- 运维成本：内置心跳与顶号登录处理；玩家掉线时其座位补空指令，**不阻塞全场**
- 协作可行性：Git 分支规范 + 任务看板 + 代码评审，5 人分工明确
- 培训成本：无需专门培训，提供简明操作说明即可上手

## 8. 结论（第 7 章）要点

| 维度 | 结论 | 主要依据 |
|---|---|---|
| 技术可行性 | 可行 | 方案成熟且有公开资料；分阶段自测闸门控制风险；4 人规模性能余量充足 |
| 经济可行性（时间口径） | 可行 | 总投入 800 人时，无资金支出；可复用框架预计节省后续 200 人时以上 |
| 社会可行性 | 可行 | 许可合规、内容合规、校园环境支撑、无政策障碍 |
| 操作可行性 | 可行 | 上手与部署门槛低，运维简单，协作流程清晰 |
| **总体结论** | **有条件可行，建议立项** | 需满足下列前提条件 |

**前提条件**：
1. 范围冻结：单房 4 人、不做公网运营与商业化
2. 里程碑闸门必须通过：每阶段自测未全绿不进入下一阶段
3. 素材来源必须合法且登记齐备
4. 演示环境（局域网 / 回环 + 4 台设备）需提前验证

**结论的解释（7.2 节）**：说明为何是"有条件"而非无条件可行 —— 结论建立在
"范围受控 + 阶段闸门有效 + 人力与周期按计划"三个假设之上；
若任一假设不成立，按第 4 章敏感性预案降级，**核心联机闭环仍然可交付，因此总体结论不反转**。
