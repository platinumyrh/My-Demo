# 第 6 章 社会可行性分析

社会可行性分析考察项目在法律法规与政策、社会公共环境以及实际操作层面是否具备落地条件。本章的依据为项目拟定范围：高校课程设计、单房 4 人局域网演示、不公开发行、不涉及商业运营。

## 6.1 社会法律政策可行性

**软件与引擎许可。** 客户端引擎拟采用 Unity 2022.3 LTS 个人版，在课设与学习用途下无授权障碍；服务端拟采用 .NET 8 控制台程序，协议代码由 protoc 生成，版本管理使用 Git。上述工具与平台均可免费获得，小组计划保留其许可信息。

**美术与音频素材。** 项目明确不做真实商业 IP 美术资产，计划只使用明确标注可免费商用的开放素材来源（如 CC0 与同等免费授权），并逐项登记来源与许可证，形成素材台账。来源不明的素材不采用，以保证资源可追溯、可核查。

**第三方库许可证。** 拟集成的第三方库包括 Protocol Buffers（BSD 系许可）、Lua 绑定库（MIT 许可）等。计划在文档中列明所用库的名称、用途与许可证类型，并保留原始版权声明与许可证副本。

**内容合规。** 系统定位为校园内的非商业演示与教学用途：不渲染血腥暴力，不设置赌博机制，不含内购与广告。项目仅在校园内演示、不公开发行，因此不涉及版号申请与网络运营资质；范围已排除公网运营与匹配排位，也避免了面向公众提供服务的合规义务。

**数据与隐私。** 系统计划只使用临时测试账号，不采集任何真实个人信息；账号口令计划以哈希方式存储，服务端不保存明文口令。演示期间产生的指令与对局数据仅用于联机功能验证。

**学术诚信。** 所有引用文献、开源实现与素材来源计划在参考文献与致谢中登记，不使用未授权的代码与资源。本项目参考公开文献中的通用方案（如确定性帧同步、客户端预测与回滚）进行自主实现。

## 6.2 社会公共环境可行性

**校园网络与实验室条件。** 演示环境为校内实验室局域网或本机回环，4 人同房对战。按估算，单客户端上行带宽量级为每秒数百字节到 1 KB 以内，下行（含多帧合包）为每秒数 KB 量级，远低于局域网承载能力。服务端为单文件控制台程序，局域网内任意一台机器均可充当服务端，实验室现有条件足以支撑演示。

**目标用户接受度。** 目标用户为同学与评审教师，对多人在线对战这一形式接受度较高；本项目采用俯视角操作，理解门槛较低，便于在演示与答辩场景中快速说明。

**与同类课设的差异化。** 同类课程设计多为单机项目，可联机构成明显差异化。本项目以确定性帧同步、客户端预测与回滚、状态哈希逐帧比对等机制体现知识点深度与验证手段，差异化不只体现在功能标签上。

**硬件门槛与演示便利性。** 项目采用俯视角、单房 4 人的小型场景，硬件门槛低，普通笔记本电脑即可运行。4 台设备在实验室内即可完成同房对战，便于答辩现场演示。

**社区分享的正向外部性。** 完成课设后，小组可向学习社区分享技术总结，例如帧同步的实现要点与确定性自测的组织方式，以降低后续同学的学习门槛，具备正向外部性。

## 6.3 操作可行性

**使用门槛。** 客户端操作拟为 WASD 移动配合鼠标瞄准与开火，用户流程为登录、房间、开战三步：输入账号密码完成登录校验后进入大厅；在大厅创建房间或从房间列表加入；进入房间后由房主开局进入对战。三步流程清晰，操作说明可压缩到一页内。

**部署难度。** 服务端为单文件控制台程序，双击即可启动；客户端为普通桌面程序，用户侧无需安装数据库或中间件。演示前需确认的主要是默认端口 7777 的占用情况与设备入网状态，两项均计划写入演示前检查清单。

**运维成本。** 系统拟内置心跳与顶号登录处理：客户端每 2 秒发送一次心跳，用于识别异常掉线与重复登录。玩家掉线时其座位以空指令补空，封帧超时 200 ms 到期即补空推进，因此个别玩家的缺失不会阻塞全场。

**协作可行性。** 小组共 5 人，计划采用 Git 分支规范、任务看板与代码评审相结合的方式，分工覆盖客户端、服务端、确定性逻辑、工具链与测试文档。每个里程碑以自测全绿作为验收闸门，模块接口以协议消息规划与核心参数表为共同基准。

**培训成本。** 操作与部署均不依赖专业知识，无需专门培训，提供简明操作说明即可上手；开发侧的能力补齐计划分摊至各里程碑，也不额外引入集中培训环节。

# 第 7 章 结论

## 7.1 可行性研究结论

综合前文分析，本项目在技术、经济（时间口径）、社会与操作四个维度的结论如下表所示。

| 维度 | 结论 | 主要依据 |
|---|---|---|
| 技术可行性 | 可行 | 方案成熟且有公开资料；分阶段自测闸门控制风险；4 人规模性能余量充足 |
| 经济可行性（时间口径） | 可行 | 总投入 800 人时，无资金支出；可复用框架预计节省后续 200 人时以上 |
| 社会可行性 | 可行 | 许可合规、内容合规、校园环境支撑、无政策障碍 |
| 操作可行性 | 可行 | 上手与部署门槛低，运维简单，协作流程清晰 |
| **总体结论** | **有条件可行，建议立项** | 需满足下列前提条件 |

上述四项条件是结论成立的前提。它们共同构成项目的可行性边界；若某一条不满足，应按第 4 章的敏感性预案降级，而不是直接否定项目。

1. **范围冻结。** 保持单房 4 人、不做公网运营与商业化、不做匹配排位与社交系统的既定边界，任一方向的扩张都将冲击 800 人时基准与 16 周周期。
2. **里程碑闸门必须通过。** 每阶段自动化自测未全部通过不得进入下一阶段，尤其确定性基础库、逻辑世界、客户端预测与回滚三个环节，须以状态哈希逐帧比对的一致结果作为验收依据。
3. **素材来源合法且登记齐备。** 美术与音频素材须来自明确标注可免费商用的来源并逐项登记许可证；第三方库须列明许可证类型并保留声明。
4. **演示环境需提前验证。** 局域网或本机回环环境、4 台设备与默认端口 7777 的可用性须在演示之前完成验证。

## 7.2 结论的解释

本节说明为什么结论是有条件可行而非无条件可行。其成立依赖三个假设：范围受控、闸门有效、人力与周期按计划。

第一，范围受控。确定性帧同步涉及协议、逻辑、预测与回滚多个环节，范围不冻结则功能持续膨胀，工时与测试覆盖面都难以收敛。第二，阶段闸门有效。团队已具备 C# 与 Unity 经验，但 UDP 网络编程与确定性模拟属待补齐能力，只有把学习与验证切分到各里程碑并由自测闸门逐关拦截，才能避免问题集中到后期爆发。第三，人力与周期按计划。800 人时基准的前提是 5 人、16 周、每人每周 10 小时。

若上述假设中任一条不成立，项目将按第 4 章的敏感性预案降级：每周工时下降时削减资源热更与表现层内容；周期压缩时把房间人数降为 2 人并关闭资源热更；人力减少时把 5 套自测套件缩减为 3 套。这些措施削减的是外围功能与测试覆盖面，由确定性帧同步、协议编解码与预测回滚构成的**核心联机闭环仍然可以交付**，课程设计的核心目标仍然能够达成，因此总体结论不因降级而反转。

综上，在范围冻结、闸门有效、投入按计划、素材与演示环境准备到位的前提下，本项目在技术、经济、社会与操作四个维度均具备可行性，建议按计划立项。

## 附录 A 协议消息一览表

协议包格式为 `MsgID(4 字节) + Length(4 字节) + Protobuf 载荷`，消息 ID 按用途分区段规划。下表按区段整理拟定消息。

| 区段 | 用途 | 代表消息 |
|---|---|---|
| 1–2 | 心跳 | `C2S_HeartBeat`、`S2C_HeartBeat` |
| 10–20 | 房间管理 | 创建房间、加入房间、离开房间、房间列表、玩家进出广播、房主开局 |
| 30–31 | 帧同步（第一代方案） | `C2S_PlayerInput`、`S2C_FrameState` |
| 50–51 | 游戏控制 | `S2C_GameStart`、`S2C_GameOver` |
| 70–71 | 登录认证 | `C2S_Login`、`S2C_Login` |
| 80–83 | 战斗事件 | 开火上报、开火广播、死亡上报、死亡广播 |
| 90–91 | 帧同步（第二代主方案） | `C2S_LockstepCommand`、`S2C_LockstepInputs` |

其中第二代帧同步区段为主方案，客户端只上报量化后的输入指令，服务端只做封帧与广播，不持有游戏状态；第一代状态同步消息保留为方案对比与历史设计说明。

## 附录 D 确定性自测用例清单

计划提供 5 套确定性自测套件，均在编辑器菜单中一键运行，合计约 50 条断言。各套件与其主要断言要点如下表。

| 套件名称 | 主要断言要点 |
|---|---|
| 确定性基础库自测 | 定点数四则运算与精度；方向表全角度抽检；环绕角差值计算；开方精度；随机数同种子产生同序列 |
| 逻辑世界自测 | 双世界 300 帧逐帧状态哈希一致；指令敏感性；走与冲刺位移定量；斜向归一化；转向限速不超调；碰撞互推对称且中点守恒；完全重合兜底；死亡后不响应指令；边界钳制；跳跃落地不穿地 |
| 客户端预测自测 | 即时确认零回滚；预测命中零回滚；预测落空触发回滚且回滚校正后终态与参照一致；乱序投递；重复投递幂等；迟到指令回滚生效；发送队列一次性取走；快照还原保真 |
| 战斗逻辑自测 | 开火节流；直射命中与落点；反向与超射程未命中；最近目标优先；击杀判定；死者不挡弹（穿透）；死亡射手停火；空仓自动换弹；手动换弹；含战斗的随机 300 帧双世界一致；战斗敏感性 |
| 协议转换自测 | 单条指令与批量指令往返；字节级收发往返；全链路回环（客户端发送 → 打包上线 → 服务端顺序封帧 → 回线喂回客户端，断言终态与直连参照一致） |

上述用例的正确性判据以状态哈希的逐帧比对为核心，而非抽样检查；每套件全部通过方可作为对应里程碑的验收闸门。

## 附录 E 术语表

| 术语 | 解释 |
|---|---|
| 帧同步 | 各客户端只交换输入指令，并用同一份确定性逻辑独立演算，从而得到一致的对局结果，服务端主要承担指令汇集与广播职责 |
| 确定性 | 给定相同初始状态与相同指令序列，任何平台与任何一次运行都产生逐位相同的结果 |
| 定点数 | 用整数按固定小数位表示实数，本项目拟定采用 Q16.16，以规避不同平台与 CPU 的浮点运算差异 |
| 逻辑帧 | 游戏逻辑推进的最小时间单位，本项目拟定逻辑帧率为 15 Hz，即每帧 66.67 ms |
| 输入延迟 | 本地第 N 帧的输入指令在第 N+2 帧生效，本项目拟定延迟为 2 帧，约 133 ms |
| 预测 | 客户端在权威指令到达之前先按本地输入推进逻辑，以消除输入延迟带来的手感迟滞 |
| 回滚重演 | 权威指令到达后发现与预测不一致时，回滚到分歧帧之前的快照并重新演算，使终态与权威结果一致 |
| 封帧 | 服务端在某一逻辑帧的全员指令到齐后立即确定该帧内容并广播；到期未收齐则按超时补空指令处理，到期时间为 200 ms |
| 快照 | 某一逻辑帧的完整逻辑状态副本，用于回滚重演时还原到指定帧 |
| 状态哈希 | 对帧号、玩家 ID、坐标、朝向、血量、弹药与生死做纯整数混合哈希，用于跨端逐帧比对是否发生漂移 |
| 权威 | 对局结果的最终裁定来源，本项目通过确定性演算与状态哈希比对间接获得一致性，服务端不持有游戏状态 |
| 持留最新指令 | 某帧缺少某玩家指令时的容错策略，按空指令处理并保持该玩家不卡帧，避免个别缺失阻塞全场推进 |
